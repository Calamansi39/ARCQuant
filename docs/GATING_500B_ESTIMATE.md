# 500B 级模型的 gating / 稀疏校准时间估算

更新时间：2026-11-05。

## 先澄清“gating”是什么

本项目里有三件容易混淆的事情：

1. **DeepSeek 原生 MoE router**：checkpoint 中已经有训练好的 `Gate` 权重。我们做推理和稀疏评测时直接使用它，不需要重新训练。
2. **TEAL 的门控规则**：不是一个神经网络。离线收集投影输入的有符号激活直方图，然后从分位点得到阈值；在线比较 `abs(x)` 和阈值。
3. **WINA 的门控规则**：uniform 模式也不训练网络。加载权重后计算输入列的 L2 范数，在线用 `abs(x) × column_norm` 做 top-k。只有逐层 greedy 分配才需要反复前向搜索稀疏率。

因此，当前 50%–90% 的 TEAL/WINA 实验不需要“训练 gating 模型”。同一份校准统计可以支持多个稀疏度：TEAL 只需换分位点，WINA 只需换 top-k 数量，不必为每个稀疏度重新跑大模型校准。

## 本机已有大模型的可测基准

DeepSeek-V4-Flash-0731 当前 checkpoint 的索引总大小约 **166.9 GB（155.4 GiB）**；TP2 转换后每张 H20 约 80 GB，当前部署需要两张约 140 GiB 的 H20。配置包含 43 层、256 个 routed experts、每 token 激活 6 个 routed experts 和 1 个 shared expert。

现有 `calibration80` 不是正式校准，而是 1 个 WikiText-2 片段、64 token 的 smoke 产物。manifest 中 TP2 两个 rank 的最长记录约 **75.8 秒**，因此可以先得到一个保守的线性上界：

```text
128 个片段 × 512 token / 64 token × 75.8 秒 ≈ 77,619 秒 ≈ 21.6 小时（TP2 墙钟）
```

实际时间可能低于或高于这个值，因为长序列会改变缓存、专家路由和 kernel 利用率；这个数字只用于排卡，不能当作实测承诺。按两张卡计算，该上界约为 **43.2 GPU 小时**。

## 推荐的时间预算

| 工作 | 是否需要训练 gate | 当前代码状态 | 两张 H20 的粗估 |
|---|---:|---|---:|
| TEAL uniform，复用现有 histogram，生成 50/60/70/80/90 阈值 | 否 | 已支持 | 分钟级，主要是 CPU/文件处理 |
| WINA uniform，复用权重列范数，生成 50/60/70/80/90 top-k | 否 | 已支持 | 分钟到数十分钟，通常不需要重新跑完整校准 |
| DeepSeek 正式 TEAL histogram 校准，128×512 token | 否 | 已有入口，旧目录仅 smoke | 约 8–24 小时墙钟，建议预留 1 天 |
| DeepSeek 正式 WINA 列范数准备 | 否 | 运行时按真实权重计算 | 通常低于一次完整校准；以实际加载日志为准 |
| 每个稀疏度 MATH-500 生成评测 | 否 | 已排队 | 由题目生成长度决定；当前 50% WINA 已显示可能超过 1 天 |
| 逐层 greedy 稀疏率分配 | 否，但需要大量误差搜索 | DeepSeek 专用路径尚未实现 | 预计至少数天到数周，不建议作为第一轮 |
| 从零训练一个新的 gating 网络 | 是 | 当前项目没有该训练目标 | 不能仅凭现有代码估算；需要训练数据、损失和分布式训练方案 |

## 为什么 500B 级 greedy 会很慢

现有 Llama greedy 校准的思路是：每层对 7 个投影反复尝试候选稀疏率，并用多个校准序列做前向误差比较。以目标 90%、步长 0.025、16 条 greedy 序列为例，单层大约有 `36 × 7 × 16` 次候选层前向；43 层累计约 17 万次层前向。这不是一次普通校准，而是大量重复搜索。

DeepSeek 还有 MoE、MLA、grouped `wo_a` 和 TP 路由，不能直接把 Llama greedy 代码套过来。若要做 DeepSeek 的 greedy，需要先定义专家路由、分组投影和跨 rank 误差的目标，再实现并验证；在此之前，uniform TEAL/WINA 才是可控方案。

## 迁移到其他服务器时的建议

- 至少按 **TP2** 预留两张显存约 140 GiB 的卡；若改 TP 并行度，必须重新生成转换权重和校准文件。
- 校准和评测使用同一模型 config、TP checkpoint、外部 runtime 和 ARCQuant commit；manifest 会校验这些签名。
- 先用 1 题和 8 题验证，再跑 500 题；90% 极高稀疏度尤其要检查 EOS、有限 logits、答案提取和实际 mask ratio。
- 不要为每个稀疏度重复做 128×512 校准。先完成一份正式 TEAL histogram 和一份 WINA norm 准备，再复用到五个目标点。
- 当前实现仍是 dense GEMM 加 mask，稀疏统计不能直接换算成真实端到端加速。
