# DeepSeek Tiny 截断分析

截至 2026-11-12 11:02 CST。本文读取 `runs/deepseek_tiny_sweep_20261106/` 中已经写盘的逐题结果；WINA 70% MATH 仍只有 80/100 题，因此涉及该单元的合计数字是阶段性数字。

## 先给结论

1. `finish_reason=length` 的含义很明确：模型生成了 **8192 个新 token**，评测器停止继续生成。它不是显存不足，也不是输入题目被截短。
2. **50% 的 MATH 截断主要像预算或终答提交问题。** TEAL/WINA 的截断分别为 6/100、7/100；没有截断的题分别答对 94/94、93/93。CPU 审计没有在这 13 个样本中发现明确的尾部循环。
3. **60% 的 MATH 仍有较高的非截断准确率，但截断明显增加。** TEAL/WINA 截断为 28/100、43/100；没有截断的题分别答对 71/72、57/57。已保存的 71 个截断样本中，只有 WINA 60% MATH 的 1 个样本被明确标记为尾部重复，其余更像长时间反复检查、没有交出最终答案，不能全部当作“胡言乱语”。
4. **70%–80% 开始出现真正的生成退化。** 已审计样本中能看到单字符/短词/短语循环、乱码、不断重复同一算式或选项。增加上限可能救回少量“还在正常推理”的题，但不能把所有高稀疏度零分解释成预算误伤。
5. **90% 没有长度截断，但仍然全部没有有效答案。** 两种方法的 GPQA 32/32、MATH 100/100 都是 `incomplete_thinking`；这说明“没有触顶”不等于生成正常。

## 截断的几种实际形态

### 1. 仍在正常推理，预算耗尽

典型形态是输出尾部仍是连贯的数学或科学推导，模型在重新检查条件、改写算式或解释题意，但没有产生 `</think>` 后的最终答案。TEAL/WINA 50% MATH 的截断主要属于这一类；例如保存的尾部仍能读出完整的题意分析，只是停在中间。

这类题是最可能被更大预算改善的部分，但只能通过重跑验证。当前评分器不会从思考草稿中挑出一个看似正确的数字，因此正式表中仍按截断计错。

### 2. 预算耗尽前已经进入重复或乱码

典型形态包括：同一个短词、符号、数字或选项持续重复；反复生成同一个算式；出现大量无意义字符；在同一段自我检查中循环。已有 CPU 审计明确标记了这些尾部重复：

- TEAL 70%：GPQA 9/31，MATH 10/100；
- WINA 70% GPQA：9/32；WINA 70% MATH 在旧的 60/100 快照中已有 9 条，当前新增的 20 条中又能看到明显的 `?`、中文字符和短语循环；
- TEAL 80% MATH：3/83；
- WINA 80% GPQA：27/31；WINA 80% MATH：74/97。

这些数字是保守的“明确尾部重复”标记，不是对所有退化样本的自动完美分类。未被标记的样本也可能已经推理失稳，只是没有形成规则性重复。

### 3. GPQA 的强制关闭 thinking

GPQA 当前不是简单地给模型 8192 个自由 token。协议是：

```text
总上限：8192
thinking：最多 7167 个 token，再加 1 个 </think> 关闭 token
最终答案预留：约 1024 个 token
```

50% GPQA 中，TEAL/WINA 分别有 17/32、18/32 题触发强制关闭 thinking；其中 14、17 题最终仍达到总上限。60%–80% 时几乎所有题都在 thinking 边界附近或最终总上限附近结束。

强制关闭 thinking 本身不是错误，也不是长度截断；若模型随后自然输出选项并 EOS，题目仍可正常评分。但本轮很多题在被关闭后继续写推理，没有提交明确选项，最后又触发 `length`。这说明 GPQA 的问题既有模型生成变慢，也有当前“7168 thinking + 1024 final”分配不适合高稀疏输出的问题。

### 4. 90% 的提前 EOS

90% 任务大多很快输出 EOS，但思考没有闭合，也没有有效最终答案。它们不是“预算不够”，而是模型已经在严重退化后提前停止。因此把上限从 8192 调大，预计不会自动修复 90% 的问题。

## 8192 是否合理，下一步用多少

### 当前正式结果：继续用 8192

本轮的 `max_new_tokens=8192` 与原先 DeepSeek 生成式评测协议一致，当前表格也按这个协议生成。若要比较 BF16、HiF4、TEAL、WINA，必须保持相同上限；否则准确率差异会混入预算差异。

8192 对 50% MATH 基本够用，但已经有少数长推理题在最后一步没有交答案。它对 60% 以上的稀疏度暴露出生成稳定性问题，不能据此断定所有截断都是预算误伤。

### 诊断实验：先试 16384，不直接上 32768

如果目的是判断“延长预算能救回多少题”，我建议先用 **16384 总新 token** 做小规模配对试验：同一题、同一 seed、同一 ARC/稀疏策略，只比较 8192 与 16384。先跑 50% 和 60% 的少量开发题，记录：

1. 截断率是否下降；
2. 非截断准确率是否保持；
3. 明确重复/乱码比例是否下降；
4. 总 token 数和卡时增加多少。

如果 16384 只把重复文本延长，没有明显增加有效终答，再上 32768 只会浪费卡时。

对 GPQA，单独把 `max_new_tokens` 改成 16384 **不会自动把 thinking 上限从 7167 提高**，因为当前代码仍会把 thinking 上限限制在 7167。要测试更大的思考预算，必须显式修改并固定新的协议，例如“约 12288 thinking + 4096 final”，然后让所有对照重新使用这套协议。这个诊断协议不能直接和当前 8192 结果混成同一张正式结果表。

## 最终判断

当前截断不是单一原因：

- 50% MATH：主要像预算和终答交付不足，扩大预算有希望恢复一部分；
- 60% MATH、50%–60% GPQA：预算问题和稀疏导致的长推理混合，扩大预算值得小规模验证；
- 70%–80%：已经出现明显重复、乱码和推理循环，不能只靠增大预算解决；
- 90%：主要是提前失稳和思考未闭合，和长度上限关系较小。

因此，正式结果暂时继续按 8192 token 报告；16384 只作为控制“预算误伤”的诊断对照，不能事后把原表中的截断题改判为正确。
