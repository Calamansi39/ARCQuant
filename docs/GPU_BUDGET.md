# GPU 卡时粗估（2026-10-27 核对）

**卡时 = GPU 张数 × 实际运行小时数。** 下面把模型能否启动、评测规模和耗时估计分开列。当前机型为 8 张 H20-3e，每张约 140 GiB 显存；权重文件占用的磁盘大小不能直接当作推理显存。

## 启动所需卡数

| 模型与现有评测后端 | 已验证或要求的卡数 | 说明 |
| --- | ---: | --- |
| DeepSeek V4 Flash，文本基线 | 2 张 H20 | 已有两卡转换权重和服务器原有的四精度完整基线结果；本仓库的 GPQA 小样本 CPU 预检通过。 |
| MiniMax H3，VBench 文生视频 | 1 张起，最多动态使用 8 张 | 服务器原有四精度 VBench Tiny 结果；本仓库的 Tiny 生成/评分 CPU 预检通过。每个生成 worker 至少需要约 79,000 MiB 空闲显存。 |
| MAGI-2 preview，VBench 文生视频 | 2 张 H20 一组 | 现有 CP=EP=2 入口已用真实权重完成短步生成；官方示例用 8 卡。两卡正式运行仍需持续空闲显存和大量主存。 |

这些是本机已有 `base_eval` **基线**入口，不表示 ARCQuant 的残差通道、TEAL 或 WINA 已适配上述新模型。ARCQuant 原有 Llama 路径的 `HiF4` 是数值模拟，不能按真实压缩后的 4-bit 显存预留卡。

## 文本评测先用小规模测时

CLI 的 `smoke` 档分别取 GPQA Diamond 8 题、MATH-500 8 题、LongBench v2 8 题和 LiveCodeBench v6 2 题。DeepSeek 使用 2 卡，卡时应按 **2 × 实测墙钟小时**计算。GPQA 和 MATH 的已有协议最多生成 8192 token；LongBench v2 有 128K 长输入，LiveCodeBench v6 还有长代码生成与执行评分。题目数相同也不能用同一单题耗时估算。先用 `python arc.py plan --backend base-eval ... --profile smoke` 检查参数，再记录实际加载时间、每题耗时和峰值显存。

## VBench 的真实任务量

VBench `tiny` 是 **108 条唯一提示词，但每种精度需生成 740 条视频**；`official` 是 944 条提示词、每种精度 **6220 条视频**。原因是大部分提示词每条采样 5 次，闪烁维度还需 25 个候选并按官方 RAFT 规则筛选。Tiny 视频能复用于 official，同一种精度从 tiny 扩充时再补 5480 条。评分、失败重跑与模型加载另计。

| 模型与单种精度 | Tiny 740 条 | Official 6220 条 | 依据 |
| --- | ---: | ---: | --- |
| MAGI-2 HiF4，2 卡 | 约 **1411 卡时**（29.4 天墙钟） | 约 **11860 卡时**（247 天墙钟） | 已有两卡真实权重 2+1 步计时，外推官方 100+5 步为约 57.2 分钟/视频；不是整套实际运行结果。 |
| MiniMax H3，假设 5 分钟/视频 | 约 62 卡时 | 约 518 卡时 | 仅供排期演算，尚无本轮真实单视频测速。 |
| MiniMax H3，假设 20 分钟/视频 | 约 247 卡时 | 约 2073 卡时 | 同上；多卡并行可缩短墙钟时间，卡时大致不变。 |

MAGI-2 的既有短步外推还给出四种精度顺序执行 tiny 总计约 **118.4 天墙钟**，在同一两卡组上约 **5683 卡时**，未计评分、重试和首次文本编码。把 preview 降到 50 步可缩短时间，但会改变质量协议，不能与官方 100+5 步结果混合。上述 MAGI 数值的来源、计时条件和局限见取得访问权限后的 `external/base_eval/README.md` 的 MAGI-2 小节。

## 实验排期顺序

1. 先在 [资产与基线指南](ASSETS_AND_BASELINES.md) 中确认权重和数据，并用 `python arc.py assets` 复查。
2. 文本任务先跑对应 `smoke` 档，记录两卡实际墙钟时间，再据此扩大样本数。
3. 视频任务先生成一条**完整步数**视频测时；再决定是否做 740 条 tiny。不要把 2+1 步调试视频当作正式吞吐。
4. Terminal-Bench 当前已下载 86 个任务，但还未接模型服务、代理和 Docker 运行；它的卡时取决于选定任务与服务方式。
